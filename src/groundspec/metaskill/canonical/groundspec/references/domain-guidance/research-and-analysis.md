# Domain guidance: research and analysis

Select `--domain research`. The pack expects an explicit, answerable research question (not a vague topic), primary sources preferred over secondary summaries, recency checked against the task's needs, citations placed next to the claim they support (not only in a bibliography), contradictory evidence surfaced rather than silently resolved, inference labeled distinctly from directly observed evidence, and quotation kept short.

Practical tips specific to this Skill's workflow:

- If `brief.goal` reads like a topic ("look into X") rather than a question ("does X exceed Y, and by how much"), that's a `blocking` clarification per `clarification-policy.md` -- ask for the actual question before researching.
- **Network research is an external action** (see `execution-and-verification.md`'s Authorization section) -- confirm it's actually authorized before running a single search, regardless of how obviously useful it would be. If the user prohibited external actions, do the analysis with what's already available and label every claim that would have benefited from a source you couldn't check as `RESEARCH_NEEDED`, not `SOURCE_VERIFIED`. Never treat "the task is research-shaped" as implicit permission to go online.
- Groundspec has no built-in ability to fetch external sources itself; whatever tools are actually available in this session (web search, document reading, etc.) do that work *once authorized*, and their outputs go into `status.verified_facts` with a source and access date -- but only if you actually opened and read the source (`SOURCE_VERIFIED`; see `execution-and-verification.md`'s evidence taxonomy). A search-result title or snippet is not that. Do not claim a source was checked if it wasn't, and never assert "no source exists" from a bounded search -- only that none was found in the searches actually performed.
- Number of sources is not a quality signal by itself -- one authoritative primary source beats five secondary summaries repeating each other.
- When sources disagree, record both positions and which one you judge more reliable and why, rather than picking one silently -- see `examples/02-market-research` for the shape this takes in a contract's acceptance criteria.
- If the question touches medical, legal, financial, or safety territory, add the `high_stakes_regulated` risk overlay (see `routing-and-risk.md`) even though the domain pack is `research` -- the two are independent axes.
- **Authority-aware evidence for regulated claims:** for a legal, regulatory, tax, financial, medical, or safety claim, actively prefer the responsible government body, regulator, statute, official regulation, or official guidance -- record it as `PRIMARY_SOURCE_VERIFIED` in `status.claim_ledger` (see `execution-and-verification.md`'s "claim ledger" section) only if you actually opened it and it supports the exact claim including its conditions. A professional advisory article or reputable news report is legitimate *provisional* support (`SECONDARY_SOURCE_SUPPORTED`), never a substitute for the primary source -- disclose the lower authority level and state in `limitations` that official confirmation is still required. Never generalize a conditional rule (exceptions, thresholds, jurisdiction, supplier categories, dates) into a universal one because the general shape of the rule is what you found first.
- **Recency of regulatory sources:** laws and regulations get amended and supplemented by implementing regulations, so a regulatory source that is old relative to today may describe superseded rules. Always fill `publication_date` (as `YYYY`, `YYYY-MM`, or `YYYY-MM-DD`) and `access_date` on every regulatory ledger entry. When the source is more than 24 months older than the access date, or its date cannot be established, say so in `limitations`, look for later amendments or implementing regulations before relying on it, and keep the claim at `SECONDARY_SOURCE_SUPPORTED` or `RESEARCH_NEEDED` unless the official current text was actually read. `groundspec evaluate` prints an advisory note for any `legal_or_regulatory_feasibility` claim whose source date is missing, unparseable, or more than 24 months before its access date; that note is a prompt to check, not a verdict, and it does not change the completion state on its own.
- A market-size figure, a competitor-capability claim ("platform X doesn't serve segment Y"), or a segment-behavior claim ("group Z has narrower budgets/tighter schedules") is a **material claim** the moment it shapes the problem statement, sizing, or a recommendation -- it needs a `status.claim_ledger` entry (even if the honest label is `RESEARCH_NEEDED` or `MODEL_EVALUATED`), not just a sentence in the prose with nothing behind it.
