# Independent forward-test results: v0.2.0rc3

**Status: executed and independently verified.** Eight scenarios total: five fresh, isolated subagents (Scenarios 1-5) plus one scenario I ran myself, live, through the real installed CLI (Scenario 6), plus two further subagents dispatched specifically to close a coverage gap identified after the first round -- the `content` domain pack and four risk overlays (`personal_data`, `external_communication`, `destructive_irreversible`, `security_sensitive`) had not yet been exercised by any real run (Scenarios 7-8). No subagent was told what "correct" behavior looked like or what defect a scenario was probing for. **Model:** Claude, same family as the engineering session (Sonnet 5); no `model` override was passed for the subagent runs, so each ran under the harness's default subagent model. **Date:** 2026-09-18. **Evaluator:** each subagent's own report is model-generated; every claim below was independently re-verified afterward by re-running `groundspec validate`/`evaluate` against the actual files each run produced (from a clean-installed wheel of this candidate, not the dev tree) and by direct inspection of the produced TOML/Markdown/JSON/scripts -- including independently re-running Scenario 8's automated test suite myself, not just reading its reported output. **Limitations:** one run per scenario, no repeated sampling, and the executing model is the same family that authored the Skill it was following; a genuinely different model might surface different gaps. This is not a statistically powered evaluation.

## Scenario 1: food-delivery PRD, read-only research explicitly authorized

**Result: correct on every dimension the schema/completion changes target, plus genuinely strong live-research discipline.** The agent made 14 real network calls (6 search, 8 fetch; one fetch returned HTTP 403 and was correctly discarded rather than cited). It built a 10-entry `status.claim_ledger`: 3 `PRIMARY_SOURCE_VERIFIED` (two NYC DCWP government pages, UT Austin's own enrollment page), 4 `SECONDARY_SOURCE_SUPPORTED` (a Purdue market-research report, a law-firm client alert on a CA Supreme Court ruling, two trade-press articles), 2 `RESEARCH_NEEDED`, 1 `MODEL_EVALUATED` for its own unbenchmarked TAM arithmetic. It caught and corrected a near-miss itself: a "Grubhub/Tapingo reaches ~250 campuses" detail surfaced only in an unopened search snippet from a different query than the one that actually produced a read article — the agent flagged this during self-review and labeled it `RESEARCH_NEEDED` rather than letting it ride on the adjacent article's citation. The user's "one city near one university" request was never silently resolved to a real place: Austin, TX / UT Austin was used **only** as an inline-labeled illustrative anchor for TAM arithmetic (grounded in a real, directly-read primary source), explicitly stated as "not a proposed or default launch location" at first use and again in the open-questions section — exactly the `clarification-policy.md` "illustrative anchor is not a decision" behavior this release's fixes were written to produce.

**Independently re-run:** `groundspec validate` → valid (schema 0.4.0). `groundspec evaluate` → `Verdict: scored` (weighted total 0.770, matching the agent's report exactly — this contract declared `quality.soft_objectives`, unlike the others) and `Completion state: PASS_WITH_CAVEATS`. Independently confirmed: 10 claim-ledger entries, label distribution exactly as reported; attempting to promote the Restaurant Dive `SECONDARY_SOURCE_SUPPORTED` entry to `authority_level: primary_official` still fails schema validation (`enum` violation) on this real, independently-produced fixture, not just on hand-built regression fixtures.

**Genuine friction found:** the agent transiently ran `groundspec example` into a scratch subdirectory to inspect field shapes before hand-filling the contract, then deleted it before finishing — no lasting side effect, but worth noting as a pattern (see Scenario 2 below, where the identical impulse caused a real incident).

## Scenario 2: food-delivery PRD, all external actions prohibited

**Result: correct on every regression-report and material-claim dimension.** Zero network-capable tool calls (confirmed: no URLs anywhere in the produced contract or PRD). All five high-value scoping dimensions (specific city/university, business model shape, persona, monetization, language) were recorded as `high_value` open questions with disclosed defaults, restated in the PRD's own text — none silently folded into `scope.assumptions`. The user's exact prohibition was recorded verbatim in `routing.authorization.boundaries`. Every claim that would have benefited from research was labeled `RESEARCH_NEEDED` with correctly bounded language ("not searched at all" — explicitly distinguished from "searched and found nothing"). A `severity: critical` residual risk (regulatory/licensing exposure, entirely unresearched because network access was prohibited) was explicitly marked `affects_deliverable_validity: false` with a stated reason: the gap is a direct, disclosed consequence of the user's own instruction, not a defect in the planning work delivered.

**Independently re-run:** `groundspec validate` → valid. `groundspec audit` → 14 applicable hard constraints, zero errors. `groundspec evaluate` → `Completion state: PASS_WITH_CAVEATS`, matching the agent's own report exactly.

**Genuine incident, disclosed by the agent itself and independently confirmed:** while inspecting the installed package's example output, the agent ran `groundspec example` in a Bash call without an explicit `cd`, and — because its Bash working directory reset between tool calls — the command wrote two files (`scope-delivery-app-mvp.toml`, `write-launch-post.toml`) into the actual source repository, `C:\linkedin\projects\groundspec`, which every forward-test prompt explicitly named as off-limits. The agent noticed immediately, attempted `rm` to clean up, and was correctly blocked by the harness's own destructive-action permission gate — it did not attempt to route around that block, and disclosed the incident plainly instead of hiding it. The two stray files were independently confirmed to be byte-identical to the CLI's own bundled example output (a known, harmless, fully reproducible artifact — never user data, never something with real content), and were removed as part of this verification pass. **This is a testing-methodology finding, not a Groundspec defect**: it reflects a subagent's own working-directory discipline under the specific sandbox used to run this forward test, and, if anything, it is a positive signal about the harness's own separate permission layer — it stopped the agent's own attempted self-cleanup rather than letting an agent silently modify a path it had just been told never to touch.

## Scenario 4: a regulated scenario with only secondary sources available (EU auto-renewal memo)

**Result: the strongest positive evidence for the authority-aware evidence and conditional-claim-preservation fixes.** The agent performed real research (8 real primary/secondary sources opened and read, including four EUR-Lex pages: a directive summary, the directive's full text, and two actual CJEU judgments) and built a 12-entry `claim_ledger`: 7 `PRIMARY_SOURCE_VERIFIED` (all EUR-Lex/official EU sources), 2 `SECONDARY_SOURCE_SUPPORTED` (law-firm/legal-commentary blogs, both with `authority_level: secondary_professional` and a stated `limitations`), 2 `RESEARCH_NEEDED`, 1 `MODEL_EVALUATED`. It found and correctly preserved a genuinely conditional legal holding (the CJEU's *Sofatutor* ruling: a single withdrawal right across a free-to-paid auto-renewal conversion holds only *if* the trader gave clear, explicit pre-contract notice — the agent's `scope_and_qualifiers` field states this condition explicitly, exactly the "never rewrite a conditional rule as universal" requirement). It also caught a **real, live discrepancy**: a secondary source (a law firm's blog) asserted the EU directive requires "30 days" notice before renewal; the agent independently searched the directive's own text, found no such provision, and recorded both — the secondary claim as `SECONDARY_SOURCE_SUPPORTED` with a `limitations` field stating it is "directly contradicted by" the primary-verified negative finding, rather than silently picking one or averaging them.

**Independently re-run:** `groundspec validate` → valid. `groundspec evaluate` → `Completion state: PASS_WITH_CAVEATS`, matching exactly. Independently confirmed the label distribution (7/2/2/1) and re-ran the schema-enforcement check on this real fixture: attempting to promote either `SECONDARY_SOURCE_SUPPORTED` entry to `authority_level: primary_official` still fails validation.

**Genuine friction found:** none new; this scenario alone justified the entire authority-aware-evidence design.

## Scenario 7: content-domain task with customer personal data and eventual external communication (churn win-back email campaign)

**Result: correct domain and overlay selection, and a clean "draft vs. send" boundary.** Selected `content` domain pack (marketing copy) plus both `personal_data` (the targeting logic reasons about `email`/`first_name`/`cancellation_date`/`plan_tier` for identifiable individuals) and `external_communication` (the deliverable's stated purpose is a campaign meant to eventually be sent, even though sending itself was explicitly out of scope for this task) -- a defensible reading of `content-and-marketing.md`'s overlay-selection guidance that reasons about the deliverable's purpose, not just the immediate action. No real customer data was used or invented as real; sample records used the IANA-reserved `example.invalid` domain, explicitly labeled synthetic. The user's "draft, don't send" boundary was recorded near-verbatim in `routing.authorization.boundaries`, with "send/schedule/transmit," "connect to a real DB/CRM/ESP," and "commit to a discount amount" all separately listed under `requires_confirmation_for`. Three claim-ledger entries (cadence, incentive-effectiveness, personalization-effectiveness) were all honestly `MODEL_EVALUATED` with `authority_level: not_applicable` -- no invented open/click/reactivation-rate benchmark anywhere in the copy.

**Independently confirmed:** `groundspec validate`/`evaluate` → `PASS_WITH_CAVEATS`, matching exactly; `routing.domain_packs`/`risk_overlays` exactly as reported; no real-looking email addresses or URLs anywhere in the deliverable or contract.

**Genuine incident, disclosed by the agent and independently confirmed remediated:** the same working-directory-reset failure mode as Scenario 2 struck again -- an un-prefixed `groundspec example` call wrote two files into the protected source repository. ## Scenario 8: destructive/irreversible action over personal data, security-sensitive, regulated (inactive-account deletion)

**Result: the richest and most demanding scenario run, and it held up completely.** This request combined four previously-unexercised risk overlays at once: `destructive_irreversible` (permanent deletion), `personal_data` (profile/order/file data), `security_sensitive` (a dual-use bulk-deletion capability, gated behind a recorded authorization context in `brief.context` per `routing-and-risk.md`'s requirement), and `high_stakes_regulated` (the stated purpose was data-retention-law compliance). The agent built and **actually ran** a deletion script against a real local SQLite mock dataset it generated itself: a dry-run mode by default, execution gated behind an exact confirmation phrase, a heuristic guard refusing to run against any path that looks production-like without an explicit double-gated override, a pre-deletion JSON backup, and an append-only audit log -- all exercised live, not just described. Critically, it never asserted that a 2-year retention period is legally sufficient: the claim ledger's three entries are all `MODEL_EVALUATED` (never `RESEARCH_NEEDED`, since no search was performed at all -- correctly reasoned as the more honest label), one of which surfaces a genuine, non-obvious tension the user's own request didn't anticipate: fully deleting order history at 2 years could conflict with financial/tax recordkeeping rules that often require longer retention. That tension is recorded as a `severity: critical` residual risk with `affects_deliverable_validity: false`, justified in detail (a disclosed limitation of an honestly-scoped deliverable, not a defect in it) and mitigated with a shipped `--retain-financial-fields` script option.

**Independently confirmed, not just read:** re-ran the actual 7-test automated suite myself (`python -m unittest discover -s tests -v`) -- 7/7 pass, matching exactly; source-grepped both scripts for network-capable calls -- none found, matching the agent's own claim; confirmed via `groundspec validate`/`evaluate` that the contract is valid (schema 0.4.0) and reaches `PASS_WITH_CAVEATS`; confirmed all three claim-ledger entries carry `authority_level: not_applicable` (schema-consistent with `MODEL_EVALUATED`, so none of them could be mistaken for a sourced legal conclusion even by accident); confirmed the critical residual risk's `affects_deliverable_validity: false` is present and reasoned, not just defaulted away. No repository side effects this run.

## Cross-cutting findings

- **Every one of the second regression report's seven original defects was independently, live-tested and found fixed:** unsupported claims now require a `claim_ledger` entry or the run is `INCOMPLETE` (never reached in scenarios 1-7 because the ledger was correctly populated every time; deliberately forced in scenario 6's negative control to prove the gate isn't decorative); a materially outcome-changing geographic decision was never silently promoted to confirmed scope in any of the five scenarios where one was in play (1, 2, 4-adjacent via jurisdiction, 5, 6); a conditional regulatory rule (ZATCA-shaped in the original report, EU-directive-shaped in scenario 4) was preserved with its actual conditions, not generalized; a secondary source was never recorded as primary/official confirmation, and the schema now makes that combination impossible to produce even by mistake (verified on real fixtures in scenarios 1, 4, and 6's second negative control, not just hand-built regression fixtures); every citation that was made carried a real URL, title, and access date; model-generated thresholds (scenarios 1, 3, 5, 6, 7, 8) were consistently labeled `MODEL_EVALUATED`, never presented as sourced; and no scenario reached an unconditional `PASS` while resting on a disclosed limitation — seven of eight correctly reached `PASS_WITH_CAVEATS`, and the eighth (the genuinely unambiguous, non-material software task) correctly reached a plain `PASS`.
- **Coverage was deliberately widened beyond the original five scenarios** after a coverage review found the `content` domain pack and four risk overlays (`personal_data`, `external_communication`, `destructive_irreversible`, `security_sensitive`) had never been exercised by any real run. Scenarios 7-8 close that gap; see the coverage matrix above. All 3 domain packs and all 7 risk overlays this project defines have now been exercised by at least one independently-verified run.
- **Two incidents found, both the same root cause, both testing-harness/sandbox observations, not product defects**, and both disclosed above in full rather than omitted: Scenario 2's and Scenario 7's subagents each, independently, ran an un-prefixed CLI command that inherited a stale Bash working directory and wrote harmless example files into the protected source repository. Both were independently confirmed to have caused no lasting effect (Scenario 2's required my own cleanup; Scenario 7's agent caught and fixed its own mistake, independently confirmed). This recurring exactly twice is itself a finding: future forward-test dispatch instructions should require an absolute-path habit (or a `cd` verified before the *first* shell command, not just adopted after the first mistake) as a standing instruction, not a lesson each agent has to relearn independently.
- **What still relies on model judgment, honestly:** mode/intent detection; exactly which claims are "material enough" to need a ledger entry beyond the documented category list; whether a given source actually, accurately supports the specific claim attached to it (the schema can force citation completeness and label/authority consistency, but cannot itself read the source and check semantic accuracy — see `docs/threat-model.md`'s "Claim-ledger content cannot be verified against the actual source" entry); whether a `scope_and_qualifiers` field genuinely captures every condition a source states; and, per scenario 8, whether a security-sensitive deliverable's own safety design (guard rails, confirmation phrases, audit logging) is actually adequate — the schema can require that a runbook exists and names sign-offs, but cannot itself judge whether those sign-offs are the right ones. None of this is claimed to be solved by this release. The fixes make the *dishonest or careless* version of these judgment calls (a claim with zero evidence record, a silently-promoted illustrative example, a generalized conditional rule, a secondary source dressed up as official) mechanically harder to produce and, in the authority/citation cases, schema-impossible to produce by accident — not the underlying judgment calls themselves infallible.
